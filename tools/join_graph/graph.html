Where to start optimizing

Hypotheses derived from query syntax (and, in plan graphs, measured estimates). Each card says what evidence was found, a concrete experiment and a caveat. Always measure before/after with the benchmark scripts; one change at a time. Click a card to list its supporting queries in the side panel.

Rowstore (B-tree) index: lets SQL Server seek straight to matching rows. Worth it for selective filters (e.g. ca_state = 'TX') on larger tables.

Columnstore index: compresses each column separately; fast for scanning and aggregating many rows of big fact tables. Only usable alone if it contains every column the query touches on that table.

Summary table / indexed view: pre-computed aggregates at a fixed grain (e.g. sales per month and brand). Pays off when many queries need the same or a coarser grain.

Statistics: the optimizer's row-count estimates. Large estimation errors produce bad plans even with good indexes.

Column usage across the workload

Distinct queries using each physical column in a filter (WHERE/ON compared with a value), GROUP BY, inside an aggregate function (SUM/AVG/COUNT/MIN/MAX...), or as a join key. Filters on CTE aggregate results (e.g. year_total > 0) are excluded. Click a row for details.

Query runtime and estimation accuracy

One bounded diagnostic execution per query, not a repeated benchmark. Elapsed time and optimizer cost have different units and cannot be divided to obtain a meaningful cost error. Row errors compare estimates within the actual plan with measured output per invocation, including unmapped joins.
